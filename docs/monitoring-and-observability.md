# Monitoring and Observability Architecture

## Status and scope

The reusable Terraform monitoring module, mocked tests, environment inputs,
dashboard, alarm definitions, and incident runbooks are implemented. They are
**disabled by default** in both environment roots. No monitoring resources
have been applied, no CloudWatch metrics or alarms have been observed in AWS,
no SNS subscriptions have been created, and no notifications have been sent.
Local validation uses Terraform's mocked AWS provider and requires no AWS
credentials.

The Docker CI security gate is unchanged. The outstanding HIGH OpenSSL findings
remain documented in
[`container-security-assessment.md`](./container-security-assessment.md).

## Architecture

`terraform/modules/monitoring` consumes existing module outputs and creates
CloudWatch metric alarms, an environment-specific dashboard, and optionally an
SNS topic for alarm actions. It reuses the ECS log group already created by the
ECS module; it does not create another log group or KMS key.

The module is enabled only with `monitoring_enabled = true`. Each alarm family
also requires its resource prerequisites:

- ECS service alarms require a deployment-ready ECS service, cluster name,
  and service name. The environment wiring passes a null service name until
  the ECS task definition and service pass the existing deployment gate.
- `RunningTaskCount` is omitted unless both an ECS service is deployed and
  Container Insights is enabled. It uses the `ECS/ContainerInsights`
  namespace, not `AWS/ECS`.
- ALB alarms require both ALB and target-group ARNs. The module derives
  CloudWatch suffix dimensions from their ARN resource paths.
- RDS alarms require an RDS DB instance identifier.
- The dashboard is omitted when monitoring is disabled or no usable widget
  prerequisites exist.

If monitoring is enabled before any live ECS, ALB, or RDS metrics have been
published, CloudWatch may show no data. Alarm `treat_missing_data` is
`notBreaching`; missing data is not treated as an outage. Confirm metrics have
appeared before relying on alerts.

## Alarm inventory and metric semantics

The default period is 300 seconds, with 2 evaluation periods and 2 datapoints
to alarm. All three are configurable. Metric alarms have environment-scoped
names, common environment tags, and notification actions only when an SNS
topic is configured and alarm actions are enabled.

| Area | Metric / namespace | Statistic and dimensions | Default dev | Default prod |
|---|---|---|---:|---:|
| ECS CPU | `CPUUtilization`, `AWS/ECS` | Average; `ClusterName`, `ServiceName` | 85% | 75% |
| ECS memory | `MemoryUtilization`, `AWS/ECS` | Average; `ClusterName`, `ServiceName` | 85% | 75% |
| ECS running tasks | `RunningTaskCount`, `ECS/ContainerInsights` | Minimum; `ClusterName`, `ServiceName`; only with Container Insights | below 1 task | below 1 task |
| ALB unhealthy targets | `UnHealthyHostCount`, `AWS/ApplicationELB` | Maximum; `LoadBalancer`, `TargetGroup` | >0 | >0 |
| Target HTTP 5xx | `HTTPCode_Target_5XX_Count`, `AWS/ApplicationELB` | Sum; `LoadBalancer`, `TargetGroup` | >=10/period | >=5/period |
| ALB HTTP 5xx | `HTTPCode_ELB_5XX_Count`, `AWS/ApplicationELB` | Sum; `LoadBalancer` | >=10/period | >=5/period |
| Target latency | `TargetResponseTime`, `AWS/ApplicationELB` | Average seconds; `LoadBalancer`, `TargetGroup` | >=1.5 s | >=1 s |
| RDS CPU | `CPUUtilization`, `AWS/RDS` | Average; `DBInstanceIdentifier` | >=80% | >=75% |
| RDS free storage | `FreeStorageSpace`, `AWS/RDS` | Minimum bytes; `DBInstanceIdentifier` | <5 GiB | <15 GiB |
| RDS connections | `DatabaseConnections`, `AWS/RDS` | Maximum; `DBInstanceIdentifier` | >=80 | >=160 |
| RDS freeable memory | `FreeableMemory`, `AWS/RDS` | Minimum bytes; `DBInstanceIdentifier` | <256 MiB | <512 MiB |

These are starting thresholds, not service-level objectives. Review them using
baseline traffic, target count, instance class, database growth, and incident
history before a live deployment.

`HTTPCode_Target_5XX_Count` represents HTTP errors returned by the application
targets. `HTTPCode_ELB_5XX_Count` represents errors generated by the load
balancer, for example when it cannot connect to a healthy target. Investigate
them separately.

`DatabaseConnections` thresholds are not universal. The sample values match
the current example instance classes only as provisional starting points:
development `db.t4g.micro`, production `db.t4g.small`. Before enabling the
alarm, inspect the deployed PostgreSQL `SHOW max_connections`, reserve
administrative headroom, and calculate the maximum application pool total
(maximum ECS tasks multiplied by pool size). Recalculate after class, pool,
scaling, or parameter changes. Connection saturation is distinct from
database unavailability.

The storage alarm is in bytes and is intended to provide lead time before
storage exhaustion. RDS storage autoscaling does not remove the need for an
alarm: check current free space, growth rate, configured maximum allocated
storage, and the time needed to scale. The development and production
thresholds should be adjusted for actual workload and data growth.

## Dashboard

The dashboard is named `<project>-<environment>-operations` and is rendered
with Terraform `jsonencode`. Widgets include:

- ECS service CPU and memory; running task count only with Container Insights.
- ALB healthy/unhealthy targets, request volume, target and ALB HTTP 5xx,
  and target response time.
- RDS CPU, connections, free storage, and freeable memory.
- Logs Insights widgets for HTTP 5xx/slow requests and authentication/database
  error records, using the existing ECS log group.

The Logs Insights queries use Pino request fields (`requestId`, `req.method`,
`req.path`, `res.statusCode`, and `responseTime`) and avoid request bodies,
credentials, email addresses, and tokens. Dashboard widgets do not grant
additional log access; IAM permissions are still required for operators.

## Structured application logging

Pino and `pino-http` already emit JSON logs with epoch timestamp (`time`),
numeric log level, request/correlation ID, HTTP method and path, response
status, and response duration. The request serializer intentionally excludes
headers and query strings. The logger redacts authorization, cookies, API
keys, password, secret, and token fields. Unhandled request errors record
only a safe error name and request ID, not the exception message/stack.

Readiness exceptions were previously converted to HTTP 503 without a specific
log. The handler now emits a warning containing the request ID and error
class only; it continues to return the same generic 503 response. Database
passwords, JWTs, request bodies, and exception messages are not emitted.

Example Logs Insights queries:

```text
# HTTP 5xx responses
fields @timestamp, requestId, req.method, req.path, res.statusCode, responseTime, msg
| filter res.statusCode >= 500
| sort @timestamp desc
| limit 100
```

```text
# Slow requests (one second or more)
fields @timestamp, requestId, req.method, req.path, res.statusCode, responseTime
| filter responseTime >= 1000
| sort responseTime desc
| limit 100
```

```text
# Database/readiness failures
fields @timestamp, requestId, errorName, msg
| filter msg = "Readiness check failed"
   or msg = "Idle database client error"
   or msg = "Database pool close failed"
| sort @timestamp desc
| limit 100
```

```text
# Authentication failures by route/status, without logging credentials
fields @timestamp, requestId, req.method, req.path, res.statusCode
| filter req.path like /\/api\/v1\/auth\/login/
   and res.statusCode = 401
| sort @timestamp desc
| limit 100
```

Use the `requestId` returned in the `X-Request-Id` response header to correlate
client reports. Treat request IDs as correlation metadata, not trusted identity.

## SNS notification design

Notifications are opt-in. The module supports either:

1. A caller-supplied existing SNS topic ARN. Topic encryption and its
   CloudWatch publish policy remain the caller's responsibility; or
2. `monitoring_create_sns_topic = true`, which creates the environment-scoped
   `<project>-<environment>-alarms` topic with the AWS-managed SNS KMS key
   (`alias/aws/sns`) and a topic policy that permits CloudWatch alarm publishing
   only for alarm ARNs matching the current account, region, and environment
   prefix.

No email, SMS, or webhook subscription is created. During an authorized
deployment, an operator must configure the approved subscription, confirm it
through its endpoint, and test delivery under the organization’s change
process. Do not put personal destinations or webhook URLs in Terraform.
Alarm actions can be disabled independently with
`monitoring_alarm_actions_enabled = false`.

## Alert severity and response priorities

- **Priority 1:** production readiness failure, all ALB targets unhealthy,
  sustained ALB-generated 5xx, or database unavailability. Start the
  corresponding incident runbook and notify the incident commander.
- **Priority 2:** sustained production ECS CPU/memory, target 5xx, RDS
  connection saturation, low storage, or low freeable memory. Investigate
  correlations and capacity headroom.
- **Development:** alerts are diagnostic and should not page by default.
  Production and development thresholds differ; production notification
  subscriptions are not created by this repository.

Severity is operational guidance, not an automatic paging policy. Actual
response times and notification destinations require service-owner approval.

## Development and production differences

| Setting | Development | Production |
|---|---|---|
| Monitoring resources | Disabled by default | Disabled by default |
| ECS service | Disabled until explicit deployment prerequisites | Disabled until explicit deployment prerequisites |
| Container Insights | Disabled by default; `RunningTaskCount` alarm omitted | Enabled in example configuration; task alarm still gated until service deployment |
| ECS CPU/memory thresholds | 85% | 75% |
| RDS CPU threshold | 80% | 75% |
| RDS free-storage threshold | 5 GiB | 15 GiB |
| RDS connections example threshold | 80; verify against live `max_connections` | 160; verify against live `max_connections` |
| RDS freeable-memory threshold | 256 MiB | 512 MiB |
| Existing SNS topic / create topic | Null / false | Null / false |

All values are overridable through environment variables in
`terraform/environments/{dev,prod}/variables.tf` and the corresponding
`terraform.tfvars.example`.

## Container Insights and costs

`RunningTaskCount` is a Container Insights metric. It is not created by the
standard `AWS/ECS` service CPU/memory metrics. The module omits that task-count
alarm and dashboard widget if Container Insights is disabled, or if the
service is intentionally deployment-gated. Enabling Container Insights can
incur CloudWatch charges for metrics and telemetry; check current regional
pricing and collection mode before enabling it.

CloudWatch dashboards, metric alarms, custom metrics/Container Insights,
CloudWatch Logs ingestion/storage/Insights queries, SNS notifications, and
KMS requests may incur charges. This repository does not enable these resources
by default. Public GitHub Actions validation does not call AWS or create
CloudWatch resources.

## Local validation

From the repository root, with Terraform 1.10+ and AWS provider plugins
available:

```sh
terraform fmt -check -recursive terraform
terraform -chdir=terraform/modules/monitoring init -backend=false -input=false
terraform -chdir=terraform/modules/monitoring validate
terraform -chdir=terraform/modules/monitoring test
terraform -chdir=terraform/environments/dev init -backend=false -input=false
terraform -chdir=terraform/environments/dev validate
terraform -chdir=terraform/environments/prod init -backend=false -input=false
terraform -chdir=terraform/environments/prod validate
checkov -d terraform
```

Native tests use a mocked AWS provider. SNS mocked `apply` test operations are
local Terraform test operations against the mock provider; they do not call
AWS. Do not use `terraform plan`, `apply`, or `destroy` as a substitute for
these offline checks unless separately authorized and configured.

## Future enablement and limitations

Before setting `monitoring_enabled = true`, operators must review a plan,
confirm the ECS service/ALB/RDS identifiers match deployed resources, validate
metric availability and alarm thresholds, configure alert ownership, and
decide whether to reuse or create an SNS topic. This documentation does not
authorize or perform any deployment.

Terraform configuration and mocked tests do not prove that AWS emits metrics
for a particular live resource, that alarm periods fit the service's traffic
pattern, that Logs Insights queries render as intended in a live dashboard,
or that SNS delivery succeeds. No AWS credentials, real subscriptions, test
notifications, resources, or monitoring costs were used in this implementation.
