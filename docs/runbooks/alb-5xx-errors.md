# ALB 5xx Errors Runbook

## 1. Incident description

The ALB or its targets are returning HTTP 5xx responses. Separate target
application failures from errors generated by the load balancer before
choosing a response.

## 2. Detection signals and alarms

- `HTTPCode_Target_5XX_Count`: target-generated status codes, counted with
  `Sum` and `LoadBalancer` plus `TargetGroup` dimensions.
- `HTTPCode_ELB_5XX_Count`: ALB-generated status codes, counted with `Sum` and
  the `LoadBalancer` dimension only.
- Correlate `UnHealthyHostCount`, `HealthyHostCount`, `RequestCount`,
  `TargetResponseTime`, ECS task health, and RDS readiness.
- The default alarm windows are two 5-minute periods; missing data is
  non-breaching to avoid no-traffic alarms.

## 3. Possible causes

- Target 5xx: application exception, invalid response, database failure,
  request overload, or a broken deployment.
- ALB 5xx: no healthy targets, target connection errors/timeouts, listener or
  protocol mismatch, or capacity/routing issues.
- A sudden request increase, client retries, or a long-running backend request.

## 4. Investigation steps

1. Compare target-generated and ALB-generated counts; do not conflate them.
2. Check request volume, target health, and response time in the same interval.
3. Check ALB target health reason codes and recent ECS service events.
4. Correlate application request IDs, response status, route, and duration.
5. Check database health and connection availability for target errors.

## 5. AWS CLI commands

**Read-only diagnostics**:

```sh
aws cloudwatch describe-alarms --region <REGION> \
  --alarm-names <ENVIRONMENT>-alb-target-5xx <ENVIRONMENT>-alb-load-balancer-5xx
aws elbv2 describe-target-health --region <REGION> \
  --target-group-arn <TARGET_GROUP_ARN>
aws elbv2 describe-load-balancers --region <REGION> \
  --load-balancer-arns <LOAD_BALANCER_ARN>
aws elbv2 describe-listeners --region <REGION> \
  --load-balancer-arn <LOAD_BALANCER_ARN>
aws ecs describe-services --region <REGION> --cluster <CLUSTER_NAME> \
  --services <SERVICE_NAME>
```

For metric history, use `aws cloudwatch get-metric-statistics` with
`--namespace AWS/ApplicationELB`, metric names above, `--period 300`,
`--statistics Sum`, and the exact dimensions shown in the alarm.

## 6. Application-log investigation

Use Logs Insights to find `res.statusCode >= 500`, sort by timestamp, and
correlate with `requestId`. Review safe error type/message and
`responseTime`. Authentication failures are normally 401/403 and are not
themselves 5xx incidents.

## 7. Safe mitigation steps

- **Read-only:** inspect ALB listeners, target health, ECS deployment events,
  and database metrics.
- **State-changing (approval required):** roll back a bad task definition,
  restore an approved listener/target configuration, or adjust service
  capacity. Make one reviewed change at a time; do not open target ingress to
  the internet.
- Preserve a sample of sanitized request IDs before restarting or rolling
  back targets.

## 8. Recovery verification

Confirm target health is restored, target and ALB 5xx counts return to normal,
target response time is acceptable, and both `/health/live` and
`/health/ready` succeed. Verify using a normal external request and monitor at
least one full alarm window.

## 9. Escalation guidance

Escalate target errors to the application owner, ELB-generated errors and
listener/routing symptoms to the platform owner, and readiness/database
symptoms to the database owner. Notify the incident commander if requests are
failing broadly in production.

## 10. Post-incident review checklist

- Record error class, impacted routes, duration, and customer impact.
- Capture alarm histories, target-health reason codes, and sanitized IDs.
- Identify whether the failure originated at ALB, task, application, or RDS.
- Review thresholds and update tests/runbooks if detection or attribution was
  unclear.
